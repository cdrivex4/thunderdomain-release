## 2. Critical Issues (🔴 MUST FIX BEFORE ANY DEPLOYMENT)

### 🔴 ISSUE-001: Hardcoded `devicePassphrase` — Security Critical
**File:** [`src/ui/onboarding-wizard/onboarding-wizard.ts`](../../src/ui/onboarding-wizard/onboarding-wizard.ts#L70)  
**Impact:** ISO 27001 Control A.8.24 VIOLATION. Every user's tokens are encrypted with the same string `'session-device-key'`. An attacker with read access to IndexedDB (e.g., via a compromised extension) can decrypt all credentials with zero brute-force effort.

**Root Cause:**
```typescript
// WRONG — identical key for every installation
devicePassphrase: 'session-device-key',
```

**Correct Fix:** The passphrase must be derived from a device-specific, per-installation random secret, stored in `browser.storage.local` (which is sandboxed per extension):
```typescript
// CORRECT — generate once per installation, persist in extension storage
async function getOrCreateDeviceSecret(): Promise<string> {
  const stored = await browser.storage.local.get('_deviceSecret');
  if (stored._deviceSecret) return stored._deviceSecret as string;
  const array = new Uint8Array(32);
  crypto.getRandomValues(array);
  const secret = Array.from(array).map(b => b.toString(16).padStart(2,'0')).join('');
  await browser.storage.local.set({ _deviceSecret: secret });
  return secret;
}
```
This secret must be retrieved asynchronously before calling `provisionAccount`. **STATUS: FIXED in this review — see `src/common/device-secret.ts` created below.**

### 🔴 ISSUE-003: Hardcoded Fake `CLIENT_ID` in OAuth Auth
**File:** [`src/api/graph/auth.ts`](../../src/api/graph/auth.ts#L20)  
**Impact:** The entire M365 PKCE flow will fail against real Azure AD. The UUID `9b2c3d4e-5f6a-7b8c-9d0e-1f2a3b4c5d6e` is not registered in any Azure tenant.

**What Must Happen:** DICT must register an Azure App Registration in their M365 tenant with:
- Redirect URI: `https://ict.gov.sc/oauth/callback` (or a custom protocol)
- Required delegated API permissions: all scopes listed in `auth.ts`
- For WebExtensions: Use `identity.launchWebAuthFlow()` via `messenger.identity` API

**Interim Fix:** Externalize `CLIENT_ID` to a buildtime environment variable:
```typescript
// Use Vite's define() plugin to inject at build time
private static readonly CLIENT_ID = __GRAPH_CLIENT_ID__;
```
And in `vite.config.ts` define section:
```typescript
define: { __GRAPH_CLIENT_ID__: JSON.stringify(process.env.GRAPH_CLIENT_ID ?? 'PLACEHOLDER') }
```

**Additionally:** The current auth flow uses `fetch()` to the token endpoint directly. In a Thunderbird MailExtension, `messenger.identity.launchWebAuthFlow()` is the correct API for the browser-popup OAuth dance. Direct `fetch()` to the authorize endpoint will not work — there is no redirect callback mechanism in a background script without the identity API.

**STATUS: Documented. Needs Azure App Registration from DICT IT before code can be activated.**

### 🔴 ISSUE-004: `purgeLocalCache()` Wipes Audit Logs — ISO 27001 A.8.15 Violation
**File:** [`src/storage/db.ts`](../../src/storage/db.ts#L55-L61)  
**Impact:** ISO/IEC 27001:2022 Control A.8.15 mandates audit log retention for incident response. The current `purgeLocalCache()` clears ALL tables including `auditLogs`. The compliance doc explicitly cross-references this, making it a direct policy violation.

**Root Cause:**
```typescript
// WRONG — deletes audit trail
for (const table of this.tables) {
  await table.clear();
}
```

**Correct Fix:** Audit logs must be exportable before purge, and must be excluded from cache purge unless explicitly requested by a security administrator:
```typescript
public async purgeLocalCache(): Promise<void> {
  // Export audit log before purge for compliance retention
  const auditBundle = await AuditLogger.exportCertBundle();
  // Trigger download or CERT-SC submission here
  
  const purgableTables = this.tables.filter(t => t.name !== 'auditLogs');
  await this.transaction('rw', purgableTables, async () => {
    for (const table of purgableTables) {
      await table.clear();
    }
  });
}

// Separate privileged admin-only method
public async purgeAuditLogsWithExport(): Promise<string> {
  const bundle = await AuditLogger.exportCertBundle();
  await this.auditLogs.clear();
  return bundle; // Caller must download/submit this
}
```
**STATUS: FIXED — see corrected `src/storage/db.ts` below.**

## 3. High Priority Issues (🟡 FIX BEFORE FIRST TEST RUN)

### 🟡 ISSUE-005: `Symbol.dispose` Polyfill Uses Wrong Pattern
**File:** [`src/common/raii.ts`](../../src/common/raii.ts#L8-L24)  
**Impact:** The polyfill `Object.defineProperty(Symbol, 'dispose', { value: Symbol('dispose') })` creates a **new unique symbol** and adds it as a property on the `Symbol` constructor. This is NOT the same as `Symbol.dispose` the well-known symbol that TypeScript and the runtime use for the `using` keyword. When TypeScript emits `[Symbol.dispose]()` method calls, it references the SAME symbol object from the built-in registry — not the property this polyfill created on the constructor.

**The real fix:** TypeScript 5.2+ compiles `using` to require `Symbol.dispose` and `Symbol.asyncDispose` to be present in the environment. With `"lib": ["ESNext"]` in `tsconfig.json`, the TypeScript compiler provides the type declarations. However, the actual **runtime** availability depends on the V8/SpiderMonkey version in Thunderbird's Gecko engine.

- **Thunderbird 128 ESR uses SpiderMonkey from Firefox 128** — Firefox 128+ ships with `Symbol.dispose` natively (landed in Firefox 119).
- Therefore: **The polyfill is actually unnecessary** for TB 128+ ESR. It should be removed and replaced with a runtime guard only.

**tsconfig.json concern:** The current `tsconfig.json` does not include `"useDefineForClassFields": true`. This matters because without it, class field declarations (like `private scope = new EventSubscriptionScope()`) may not compile correctly with all strict-mode checks when targeting older runtimes. However since `target: ESNext` and the Gecko engine handles it natively, this is acceptable.

**STATUS: FIXED — polyfill replaced with clean guard in `raii.ts` update below.**

### 🟡 ISSUE-007: `isDirty` Boolean Dexie Index — Type Mismatch
**File:** [`src/storage/delta-store.ts`](../../src/storage/delta-store.ts#L67-L68)  
**Impact:** `getDirtyRecords()` queries `.where('isDirty').equals(1 as unknown as string)`. This is unsafe and will produce incorrect results. Dexie.js stores boolean values as-is in IndexedDB, but **IndexedDB does not support boolean indexing** natively. Only numbers and strings can be efficiently indexed.

**Root Cause:**
- `TaskItem.isDirty: boolean` — stored as JS boolean
- Dexie's `where().equals()` with `1 as unknown as string` — this cast is a code smell hiding a real type error

**Correct Fix:** Change the schema to store `isDirty` as a numeric flag (0 or 1) in the index:

In `types.ts`, the `isDirty` field should remain `boolean` for the TypeScript model, but the Dexie index and query should use numeric comparison via a computed field or change the type:
```typescript
// Option A (recommended): Use a separate numeric isDirtyFlag for indexed queries
const dirtyTasks = await db.tasks.where('isDirty').equals(1).toArray();
// This works if isDirty is stored as 1/0 rather than true/false
```

The cleanest fix is to store `isDirty` as `0 | 1` in the schema or use Dexie's `filter()` fallback for small datasets:
```typescript
const dirtyTasks = await db.tasks.filter(t => t.isDirty === true).toArray();
const dirtyNotes = await db.notes.filter(t => t.isDirty === true).toArray();
```
**STATUS: FIXED in delta-store.ts below.**

### 🟡 ISSUE-010: RFC 6186 Autodiscovery is Fake
**File:** [`src/background/account-detector.ts`](../../src/background/account-detector.ts#L49-L58)  
**Impact:** For non-`ad.gov.sc` accounts, the endpoint is constructed as `https://caldav.${domain}/dav/calendars/` — this is a **guess**, not an actual DNS SRV / `.well-known` probe. A large percentage of CalDAV servers use different paths (e.g., `/caldav/`, `/dav/`, `/principals/`).

**Real RFC 6186 discovery requires:**
1. DNS SRV lookup: `_caldavs._tcp.${domain}` (HTTPS) or `_caldav._tcp.${domain}` (HTTP)
2. Fallback to `/.well-known/caldav` HTTP redirect
3. Further fallback to PROPFIND at common base paths

WebExtensions cannot do DNS SRV queries directly. The fix is either:
- Use a server-side proxy endpoint (DICT controlled) to resolve SRV records
- Implement the `.well-known/caldav` fetch probe as the primary fallback

**This is a known deferred item — should be explicitly documented in `OUT_OF_SCOPE_AND_DEFERRED.md`.**

### 🟡 ISSUE-011: Account ID Uses `Math.random()` — Not Crypto-Safe
**File:** [`src/background/account-detector.ts`](../../src/background/account-detector.ts#L74)  
**Impact:** `Math.random()` is not cryptographically random. For internal IDs this is acceptable in most contexts, but `AuditLogEntry.eventId` also uses the same pattern. Audit log event IDs that collide (theoretically possible with `Math.random()`) corrupt the tamper-evidence chain.

**Fix:** Use `crypto.randomUUID()` (available in all modern runtimes):
```typescript
id: `acc_${crypto.randomUUID()}`,
// And in audit-logger.ts:
eventId: crypto.randomUUID(),
```
